# 搜索证据流水线

## 产品交付契约

岗位要求、初筛、复核、交付统计、候选人详情、分享和外联使用同一份 `decision_record`。

| 决策 | 含义 | 交付行为 |
| --- | --- | --- |
| contact | 直接或等价核心工作有证据，外联前必须明确的条件均有支持 | 推荐、生成外联草稿 |
| review | 核心工作具有相关证据，仍存在需要核实的条件 | 独立待核实名单，展示证据缺口 |
| hold | 现有资料未建立充分的核心工作匹配 | 留在完整候选池 |
| reject | 有明确冲突或模型判定不适合岗位 | 留下原因供人工审阅 |

`unknown` 不等于不符合，也不等于满足。求职意愿等需候选人沟通才能确认的事实，不能阻止一个满足工作要求的被动候选人进入推荐。

不生成排名换算的百分制匹配分。`final_rank` 仅表达本次岗位下的相对顺序。

## 执行路径

1. 从原始 JD 和用户澄清构建版本化要求，保留技术替代关系、严格地域和核心工作要求。
2. 本地全文与向量检索增加地点优先通道；地点缺失者保留在广泛检索通道，后续按证据判断。
3. LLM 初筛逐项给出支持、冲突或未知，并引用提供的原始资料字段、经历。
4. 深度复核优先处理直接或等价工作证据，同时允许尚未明确排除的模糊候选进入复核预算，避免初筛的相邻标签直接导致漏选。解释从待定升级为推荐的原因；未复核者保留为 hold，不凑入推荐数量。
5. 对已确认可联系的人进行相对比较。比较提出的资格冲突需再次核实。
6. 根据实际推荐数和证据缺口，调度器决定结束或使用已授权预算补充一轮外部来源。不会以本地库总人数达到某个阈值认定覆盖足够。
7. 固化结果为 ready、partial、verification_needed 或 no_matches。零推荐完成搜索时释放岗位额度，已实际消费的资料扫描数不会因重评而减少。

## 可靠性边界

- 评估检查点绑定岗位契约、提示词版本、模型配置和资料内容哈希；每完成一次昂贵复核即保存。浏览器接口不返回工作进程的检查点。
- 结构化最终复核默认关闭长推理，比较和仲裁保持各自的阶段配置。
- 推荐文案、风险和缺失条件由逐项 assessment 生成，避免自由摘要与条件表互相矛盾。
- 结果保存在服务端；页面不再将整批候选人写入 sessionStorage。接口只传一份决策证据，删除重复原始对象、检索轨迹和初筛副本。网络失败与结果不存在使用不同提示。
- 向量与重排请求在统一服务边界处理网络、响应体超时及 408/429/5xx 重试；鉴权失败不盲目重试。
- 并发批次失败后停止排新任务，等待在途调用结束，保存完成部分后抛出错误。
- 新资料的语义表征、资料向量和经历向量通过一个数据库事务发布，避免半完成记录可被检索。
- 官方 DeepSeek 的 JSON 模式通过统一调用入口收到 schema；结构化提取和调度使用单独的推理配置。JSON 截断被明确识别，复核重试提供更充足的输出额度。
- 原始资料获取日期只说明资料来源时间，不保证人员当前所在地、兴趣或可入职状态。

真实回放脚本：`scripts/candidate-index/replay-saved-search.ts`。必须使用名字包含 QA 的隔离 Hirelix 数据库、`SEARCH_ALLOW_BRIGHT_RECALL=false`，且不提供 Bright API token。可用 `--validate-index` 验证已保存资料重新表征和入库，或 `--validate-index-only` 单独验证这一步；必须选择旧版资料且 `reused=0`，不能把缓存命中当成新索引成功。脚本也单独调用调度器生成后续来源建议，但不执行外部召回。
