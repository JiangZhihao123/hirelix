# Hirelix Personal Agent 产品设计优化方案

日期：2026-10-18  
状态：讨论稿，未批准实施  
定位：猎头的个人 AI 助理  
代码核对基线：`3709d907`；生产验证采用本次会话截至 2026-10-18 的结果，不代表未来环境状态。

> 用户把事情交给助理，助理理解目标、找回情况、采取行动，根据变化继续推进，并在真正需要用户判断时带着依据和建议回来。

本文只提出产品和交互优化方案，不代表所述能力已经实现，也不授权自动外发、调整权限或部署。方案确认后再进入实现。

## 1. 产品理解与设计目标

Hirelix 是面向独立猎头和精品猎头顾问的 Personal Agent。用户感受到的是一位持续合作的助理：理解工作背景，保留明确偏好和约定，能使用工具完成实际工作，接受纠正，并对委托范围内的后续推进负责。

邮件、简历、JD、职位库、推荐材料和提醒都是助理工作的手段。产品不围绕这些工具分别建立一套工作体系。

### 1.1 三类用户价值

| 价值 | 助理承担的责任 | 用户获得的结果 |
| --- | --- | --- |
| 掌握情况 | 找回职位要求、人选资料、沟通历史、客户反馈和承诺 | 不必反复解释前因后果 |
| 完成工作 | 整理、检索、比较、准备沟通、制作推荐、记录反馈和获授权的交付 | 得到可核对、可继续使用的实际成果 |
| 持续推进 | 按约定检查变化、跟踪等待、调整后续行动、升级真正的问题 | 不必亲自安排每一步操作 |

### 1.2 判断功能价值的标准

1. 是否帮助助理更准确地理解用户及其工作？
2. 是否让一件真实工作更容易办完或持续推进？
3. 是否减少用户的重复解释、机械操作和不必要确认？
4. 是否让用户更容易核对、纠正、暂停和接管？
5. 是否保留事实、来源、授权和结果边界？

不能用工具数量、生成文字长度或自主动作次数替代这些标准。

## 2. 产品边界

- 首版面向桌面浏览器，默认英文界面，保留现有中文支持；本文使用中文讲解交互。
- 主要业务围绕用户已有的职位、人选、资料、客户反馈和推荐交付。
- 独立外部付费人才寻访仍属于已退出的产品范围，不借此方案重新引入。
- 不新增待办中心、统一审批队列、后台任务列表或让用户维护的 Work 对象。
- 不默认托管整个邮箱，不把连接账号视为持续工作或自动发送授权。
- 不预先引入独立邮件 Agent、全量邮箱向量库、自动记忆流水线或业务工作流引擎。
- 没有日历和可用时间证据时，可以协调时间，不能声称已确认双方空闲或已发出日历邀请。
- 录用判断、薪资承诺、费用和合同等决定不能从一般性委托中推定授权。

## 3. 现状与缺口

“已有基础”表示代码中存在相应能力，不等于每个组合场景均已通过生产验收。

| 能力 | 现有基础或验证结果 | 需要补齐 |
| --- | --- | --- |
| 对话与执行 | 同一 Agent、受控工具、工作进度、停止与恢复基础 | 持续委托下的执行边界和最新状态校验 |
| 业务资料 | 职位、人选、文件、资料检索、推荐及逐人反馈 | 跨渠道来源关联、冲突处理，以及变化影响后续行动 |
| 邮件发送 | Gmail 和 Outlook 已实际发送测试邮件，有预览和回执 | 原串回复、回复全部、抄送范围、相关附件处理 |
| 邮件读取 | Outlook 已在生产检索并读取 Inbox 测试邮件，卡片展开及刷新后读取通过 | 完整往来串、增量发现、附件和覆盖范围 |
| Gmail 读取 | Google 审核未完成，当前未开放 | 审核和授权满足后进行独立真实验收 |
| 长期工作 | 提醒及周期性职位进展材料 | 一般持续委托、等待回复、按新信息继续执行 |
| 跨会话 | 历史和业务资料检索基础 | 稳定找回相关决定、授权、承诺和未完成动作 |
| 交付展示 | 成果、邮件卡片、回执和来源入口 | 按用户目标整合结果，减少中间过程噪声 |
| 可靠性 | 已有权限、版本、去重及部分结果机制 | 并发修改、用户在外部工具接管、发送结果未知时核实 |

### 3.1 本轮真实验证的启示

- Outlook → Gmail 的测试邮件约 2 秒到达，但进入垃圾邮件夹；SPF、DKIM、DMARC 均通过。具体分类原因未确认，不能宣称正常进入收件箱。
- Gmail → Outlook 测试邮件进入 Inbox，Hirelix 读取到正确发件人、收件人和正文校验码。
- 单次查信展示多张空结果和较长列表，用户承担了过多查找过程。
- 助理曾在收件证据未完整时提前概括“双向验收成立”。完成口径需要更严谨。
- 收发读取成功，只证明工具链；“读客户反馈—更新业务理解—继续推进—跨会话接续”仍需作为完整工作验收。

## 4. 信息架构：一个助理，一套共同事实

### 4.1 三个层次

| 层次 | 内容 | 责任 |
| --- | --- | --- |
| 委托 | 当前目标、范围、约束、期限和授权 | 决定助理负责什么 |
| 业务事实 | 职位、人选、关系、推荐版本、反馈、沟通记录和承诺 | 支撑判断与跨会话接续 |
| 来源和工具 | 邮件、文件、电话笔记、公开证据、发送与提醒能力 | 获取依据并执行动作 |

委托是产品语义，不要求新增同名数据库表或独立主菜单。具体数据归属应优先复用现有机制。

### 4.2 页面职责

- **对话：**交代目标、汇报结果、修改要求、请示、停止和继续。
- **职位：**查看当前要求、人选、推荐和反馈；页面修改影响后续执行。
- **候选人：**查看资料、沟通与不同职位下的判断，不建立全局好坏标签。
- **推荐：**准备、分享、实际外发、逐人反馈分别保留证据。
- **提醒：**保留明确时间约定的现有入口；不直接扩成通用待办中心。
- **设置：**账号、连接、明确偏好，以及持续委托的查看与暂停入口。持续委托控制的具体位置需与现有提醒入口一起验证，避免重复。

不新增独立邮箱主菜单。长邮件、完整往来、文件及业务详情在上下文侧栏打开，保留输入和滚动位置。默认首页仍是助理对话，不在问候时强行播报所有工作。

## 5. 核心工作场景

| 场景 | 用户示例 | 应交付的结果 | 关键边界 |
| --- | --- | --- | --- |
| 接招聘需求 | “这是 JD 和电话记录，整理清楚。” | 要求、来源、冲突和影响推进的缺口；按授权保存 | 分析不自动建档 |
| 积累人选 | “这是简历和刚聊的情况。” | 识别已有人员，保存有来源的新增事实 | 同名或事实冲突需消歧 |
| 找人比较 | “我库里谁适合这个职位？” | JD 相关的比较、依据、风险和检索覆盖 | 相似度不等于匹配结论 |
| 准备沟通 | “下午和 Anna 聊。” | 背景回顾、本次目标和待核实问题 | 不编造历史或日程 |
| 推荐交付 | “把这三个人推荐给客户。” | 合适的材料、版本、分享范围及实际回执 | 准备不等于发布或发送 |
| 吸收反馈 | “客户认为 Ben 行业经验不足。” | 对应职位和人选的反馈及后续影响 | 反馈意见与事实分开 |
| 协调后续 | “推进 Anna 的初聊。” | 找出缺口，执行授权沟通，跟踪结果 | 愿意初聊不等于已安排面试 |
| 跟踪承诺 | “下个月再联系他。” | 明确时间、背景及后续动作 | 模糊时间先澄清 |
| 安排注意力 | “今天哪些事最值得推进？” | 有依据的少量建议及可继续委托的行动 | 覆盖不全时说明范围 |

这些场景用于发现问题和验收，不构成固定工作流。

## 6. 三种委托方式

### 6.1 一次性交办

“分析这份简历”“比较三个人”“记录这次电话反馈”。目标完成即结束，不默认建立持续检查。

### 6.2 围绕一件事持续负责

“这周帮我推进 Harbor 这个职位，有客户反馈就记录，重要决定找我。”

助理结合已有指令形成可读约定，只询问影响执行的缺失边界：目标、对象、允许动作、请示事项、检查时间、结束条件和回报位置。

示例约定：

> **本周跟进 Harbor 招聘**  
> 可以：读取相关来信、记录明确反馈、准备后续沟通。  
> 对外发送和新增资料分享：按你的具体授权执行。  
> 工作日按约定检查，周五结束；有变化回到本对话。  
> 修改约定 · 暂停

这只是建议的交互形式，频率和授权内容不能静默替用户确定。

### 6.3 日常工作回顾

用户主动询问，或明确订阅某个时间的简报后，助理综合职位、人选和承诺汇报。按事情组织，可包含重要变化、已办事项、决策和等待，但不固定成首页四个栏目，也不强制每次全部出现。

## 7. 端到端交互示例

以下为虚构验收场景，不代表现有产品已全部实现。

1. 用户交代：“这周帮我推进 Harbor 产品负责人职位，先看已有的人。”
2. 助理检索 JD、客户要求、人选及历史，提出 Anna 和 Ben 的比较。明确 Ben 的资料不能证明直接带人，不把“管理过 PM”推断成直接下属。
3. 用户授权：“可以联系确认意向和时间，但不要透露客户名称。”
4. 助理核对正文、附件和链接的分享范围后执行；回报真实发送状态，记录在等谁的回复。
5. 客户邮件提出希望周四初聊 Anna。助理找到相关推荐和往来，按授权记录反馈；未获 Anna 时间确认，不承诺面试已安排。
6. 用户通过电话得知 Anna 下周才有空，并把笔记交给助理。助理更新当前事实，停止尚未发送的旧时间沟通。
7. 助理带建议请示：“Anna 下周才有空。建议向客户解释并询问下周二或周三的可用时间。”已有授权覆盖时可以直接处理。
8. 用户在新对话问“Harbor 怎么样了？”助理找回最新记录、实际回执和等待事项，不要求重新解释，不把旧草稿当成已外发事实。

## 8. 对话和成果交互规范

### 8.1 工作进行中

- 展示简短、来自真实执行的进展，提供停止和可展开详情。
- 同一目标的搜索、空结果和重试聚合在同一执行说明中。
- 独立目标分别呈现，不因重试重新打开已完成的目标。
- 不展示推测性百分比、装饰性计时或完整内部计划。

### 8.2 工作完成后

先说明结果和实际完成动作，再提供必要依据、限制及真正需要判断的问题。简单回答不强制生成文稿；没有后续决策时不机械追加选项。

| 结果 | 默认呈现 | 展开内容 |
| --- | --- | --- |
| 分析判断 | 简明结论及关键依据 | 原资料和来源 |
| 人选比较 | 紧凑比较及风险 | 人选详情、证据和 JD |
| 保存更新 | 实际修改摘要 | 对应业务记录 |
| 客户反馈 | 逐人反馈及影响 | 原始反馈、职位和推荐版本 |
| 推荐报告 | 可编辑和交付的成果 | 内容、版本和附件 |
| 邮件 | 收发对象、内容及真实状态 | 往来、附件、原邮件 |
| 持续委托 | 范围、最近结果、下次检查 | 修改、暂停、结束和历史 |

### 8.3 用户修改与接管

- “别发了”“换收件人”“Ben 暂时不推进”直接改变后续动作。
- 页面编辑和对话修改复用业务服务，避免两份事实。
- 发送前检查是否有新来信、用户自行回复、资料更新或授权撤回。
- 冲突时保留用户输入，解释受影响的部分，不覆盖用户改动。
- 已发生的动作不能伪装撤销；暂停时说明已经完成什么。

## 9. 上下文、证据和偏好

### 9.1 事实来源

业务记录是可检索的事实基础，对话承载指令和协作。邮件和文件作为来源关联到业务对象，不把全部历史无差别送入模型。

关联应综合当前指定对象、推荐交付关系、往来参与者、正文和已有记录；不能只凭姓名或主题命中。

客户说“前两个人可以聊”时，必须找到明确的推荐版本和顺序。找不到就询问，不能猜测。

### 9.2 记录必须保留的边界

- 谁说的、何时发生、何时记录、来源是什么。
- 对应哪个职位、候选人和推荐版本。
- 客户意见、候选人自述、已证实事实与助理推断分别表达。
- 同一来源重复处理不重复写入；更正保留可追溯关系。
- 缺失信息不自动解释为负面事实。

### 9.3 个人偏好

只保存用户明确要求记住的工作偏好，如推荐格式、称呼和沟通习惯。偏好不等于外发授权，不自动转为定时执行。新指令优先于旧偏好，用户能查看、修改和删除。

## 10. 自主行动与授权

| 用户指令 | 允许范围 |
| --- | --- |
| “看看、分析一下” | 读取和分析，不擅自修改或外发 |
| “整理保存” | 对象清楚的部分直接保存，冲突部分请示 |
| “按这个内容回复他” | 核对当前收件人、内容和分享范围后执行 |
| “日常收悉代我回复” | 仅限约定范围，不扩展为报价、时间承诺或资料外发 |
| “持续推进这个职位” | 按具体委托推进，不自动获得所有外部副作用权限 |

已有明确且仍有效的授权无需重复询问；内容、对象、收件范围或委托发生实质变化时重验授权。

持续授权需要保存范围和版本，执行时由确定性机制检查；不能仅靠模型说“用户已经同意”。外部邮件、附件和工具结果永远不能提供新的用户授权。

首阶段继续复用当前具体发送控制；范围明确的持续代发属于后续新增能力，必须单独设计和验收后开放。

## 11. 持续运行与异常恢复

首版持续运行建议采用定时检查；实时事件订阅以后按需要评估，不提前承诺。

内部至少承担以下责任：

- 记录上次成功覆盖的位置和时间；未检查完整不得报告“没有变化”。
- 按业务相关性合并变化，不为每封邮件产生一次通知。
- 处理前检查最新事实，写入和外发前再次检查授权、对象版本与接管状态。
- 等待回复到期时先重新查证，再执行已授权跟进或请示。
- 权限失效、额度不足、限流和部分失败分别说明；失败不推进成功检查位置。
- 暂停、结束或撤回后不启动新动作；恢复时重新读取当前情况。
- 通过已有去重、持久队列和有界重试防止重复记录和外发。

用户可查看最近成功检查、覆盖范围、下次检查、暂停状态。连接中断时明确说明从何时起未能检查。

## 12. 真实完成状态

| 证据 | 允许的结果表述 |
| --- | --- |
| 内容已生成 | 已准备好 |
| 业务写入成功 | 已保存，并提供对应记录 |
| 邮件提供商接受请求 | Gmail/Microsoft 已接受发送 |
| 只有已发送副本 | 已确认发件记录，收件尚未确认 |
| 收件侧存在邮件 | 已确认到达，并注明收件箱或垃圾邮件夹 |
| 实际收到对方回复 | 已收到回复 |
| 执行超时且结果不明 | 结果待核实，不自动重复执行 |

不得把“客户愿意初聊”写成“面试已安排”；不得在部分结果缺失时宣布整体工作完成。完成摘要应由真实操作和证据约束。

## 13. 邮件及其他工具如何接入

邮件补齐完整往来串、原串回复、抄送、相关附件、增量发现和外部已回复检测。邮件正文显示不完整或附件未读取时，不能声称已经理解全部内容。

文件解析继续复用现有能力；简历、JD 和反馈导入业务记录前检查归属与用户授权。网页和邮件都作为不可信来源，忽略其中要求扩大权限、泄露资料或改变任务的指令。

任何新工具都应接入同一套目标、上下文、授权和回执，不建立专属任务体系。工具缺失时清楚交代影响，不用模拟结果或手动替代包装成自动链路成功。

## 14. 数据、隐私与用量体验

- 初次持续委托展示读取范围和时间窗口，默认不全量导入邮箱。
- 保存工作需要的证据和用户明确保留的资料，避免重复存储无关邮件。
- 断开连接停止后续访问，清楚说明已保存业务记录的保留与删除方式。
- 邮件正文、附件缓存和长期业务证据的保留期限需在实现前确定。
- 定时检查频率、历史回查和附件处理会影响用量；在开启委托时解释，复用现有额度体系。
- 没有新变化时避免无意义的重复模型分析；额度不足时说明覆盖边界并暂停相关执行。

## 15. 技术责任与低复杂度实现

继续使用一个 Agent runtime，根据目标和观察选择工具。业务方法使用 Skill，不把场景固化成流程分支。

| 责任 | 优先复用 | 必要补充 |
| --- | --- | --- |
| 目标理解和方法 | Agent、相关上下文、Skills | 工作范围、持续委托语义和完成判断 |
| 业务事实 | 职位、人选、记录、推荐及资料服务 | 来源关联、去重和更正关系 |
| 工具执行 | 邮件、文件、检索和领域服务 | 往来串、回复、附件及增量读取 |
| 持续运行 | PostgreSQL、worker、现有调度 | 委托范围、检查位置、运行状态及暂停恢复 |
| 副作用控制 | 权限、版本、幂等和发送快照 | 持续授权版本、发送前新情况检查 |
| 展示 | 对话、详情面板、回执和未读通知 | 按目标聚合进展和结果 |

新增内部持久字段或记录必须对应具体的恢复、授权或证据需要。具体表结构留到实现设计，不以本方案预先创建新框架。

## 16. 分阶段实施建议

### 阶段一：一次完整委托办顺

范围：一个职位、多位候选人，串联资料、比较、客户反馈、业务记录、授权沟通、交付与跨会话接续。

优先补齐来源关联、完整邮件往来与回复、附件、最新事实校验和对话结果聚合。以 Outlook 做真实邮件链路；Gmail 审核通过后独立验收。

### 阶段二：同一件事持续负责

范围：明确时间和权限内的持续委托，覆盖定时检查、等待回复、用户自行接管、暂停恢复及异常透明。

先实现读取、准备和用户已授权的内部记录；持续外发单独验证，不能因启用持续检查就自动开放。

### 阶段三：多项工作的日常协作

范围：按用户请求或订阅，综合多个职位、人选和承诺安排注意力；在明确范围内开放日常代办。

不新增统一待办中心。通过所属对话和按需简报交付，用户能够追溯每项建议的依据和覆盖范围。

## 17. 验收标准

| 验收场景 | 通过标准 |
| --- | --- |
| 一个职位、多位候选人 | 比较与反馈逐人关联，判断始终属于具体职位 |
| 邮件与电话信息变化 | 新来源影响后续行动，不继续执行过时安排 |
| 同名或不明确指代 | 不猜测归属，仅询问受影响部分 |
| 用户页面修改 | 后续 Agent 执行使用最新版本 |
| 原串回复与附件 | 参与者、线程和附件正确，不泄露未授权资料 |
| 已授权动作 | 不重复索要同一授权；范围变化重新核对 |
| 用户自行回复 | 不重复外发，能够接续当前进展 |
| 跨会话继续 | 找回事实、决定、回执和等待，不要求重新交代 |
| 暂停与撤回 | 不启动新动作，清楚报告已经发生的动作 |
| 权限或网络失败 | 保留成果，透明呈现未完成部分，不误报成功 |
| 发送结果未知 | 核实后再决定，不盲目重发 |
| 检索覆盖不足 | 不把未命中解释成没有回复或没有合适人选 |
| UI 与交互 | 重点清楚、来源可查、输入不丢、无大量中间卡片干扰 |

评估同时记录工作完成质量、重复解释次数、不必要确认、人工纠正、重复副作用和恢复情况。具体效果指标的目标值在取得基线后确定，不编造提升比例。

验证分层报告：模拟回归用于错误与确定性边界；本地真实链路使用同一隔离数据库的前端与独立 worker；获授权部署后再做生产复验。模拟响应、接口 200、构建通过不能替代真实工作结果。

## 18. 需要讨论确认的产品决定

| 决定 | 建议 |
| --- | --- |
| 第一阶段范围 | 先做好一件完整猎头委托，覆盖多渠道，不按邮箱功能拆交付 |
| 持续执行默认权限 | 默认读取与准备；写入和外发依具体委托，不静默扩大 |
| 持续检查节奏 | 先定时检查，频率和时间段明确展示；暂不承诺实时 |
| 控制入口 | 对话中可改可停；设置中统一查看，不再建任务中心 |
| 邮件正文和附件保留 | 实现前确定期限、删除方式与业务证据保留边界 |
| Gmail 读取未开放期间 | 准确显示限制，不作为完整读取体验宣传 |

这些建议确认后，再补充实现拆分及交互原型。讨论稿本身不触发代码、权限或生产变更。
