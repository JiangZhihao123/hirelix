## 查到的实际缺陷

- `workspace` 名义上是目录，却把完整 JD、候选人档案和状态一起返回。`read_role` 又重复这些数据及各版本 JD，原始报告则只有消息 ID。现在目录只负责定位对象；读取角色/候选人时才返回保存记录、原始用户报告和对应记录版本。历史 JD 提供索引，不与当前要求重复混排。
- 记录更正只改正文，来源仍指向最初消息。真实样本中 158,000 已更正为 155,000，补回原话时反而重新制造了假冲突。现在更正保存当前消息 ID；读取证据时结合已有版本表与成功工具回执，恢复各版本的原始来源，不需要新表或数据迁移。消息、版本与回执查询均受用户边界约束。
- 提醒 `completed_at` 实际表示通知已送达，不表示标题里的业务动作做完。Agent 工具改为 `notification_status` / `notification_delivered_at`，不把内部调度字段直接当业务完成状态返回。
- 从优先级建议继续执行时，发现文档修改再次丢失上下文：主 Agent 看到了新事实，宽泛改写工具的内层生成只得到旧快照，保留了旧数字，随后 Agent 又创建一份文档。新增通用 `edit_document`：主 Agent 用自己已读的证据指定唯一原文及替换文本，业务服务锁定当前版本、原子修改并保留历史。精确修改与原有改写复用同一保存函数，没有猎头场景分支或文本关键词修补。

这些缺陷会影响判断，但不是对每一次模型措辞错误的单一因果证明。此次修复重点是让模型拿到可核对、时间与来源清楚的证据，而不是事后过滤回答。

使用真实 Chrome、独立本地 QA PostgreSQL、真实 DeepSeek 和独立 worker；人物、客户与资料均为虚构。继续使用同一周已保存的两个候选人和两个职位。

2. **等待期间继续工作**：问 Cedar 没回复还能做什么，找到了推荐材料中的旧区间及独立的客户待答问题。

4. **改变真实业务状态**：通过 UI 保存 Owen 面试准备完成、会议链接已核对，以及 Cedar 要求周一中午收到更新推荐材料。问只剩十分钟时，优先级转向 Cedar 交付，没有重复安排已完成的准备工作。
5. **继续执行**：宽泛改写第一次没有完成目标并生成了额外 QA 草稿，此失败未计作通过。精确修改工具接入后，原推荐材料从 v4 到 v5，数据库逐字比较证明仅 `GBP 150,000 to 170,000` 改为 `GBP 150,000 to 165,000`；原 ID、标题及其余内容不变，未再新增文档。UI 自动刷新并显示保存回执。
6. **跨对话复测**：新对话问明早的重点。Agent 从业务记录重新得出 Cedar 中午交付优先，Beacon 准备已完成、周三再跟进未答事项；没有依赖刚才对话中的建议。工具轨迹为目录/Skill、两个角色、相关文档，再交付答案。

验证过程中早先错误生成的额外 QA 草稿保留，未擅自删除。最终 QA 数据为 5 份文档、23 条记录；本轮明确新增两条沟通事实，原推荐文档 v5，其他原有文档版本未改变。没有外发邮件、生产部署或付费人才召回。
