# Hirelix：猎头 Personal Agent 的核心场景与设计原则

更新日期：2026-10-08。

本文记录产品讨论确定的方向，作为后续产品设计与开发的依据。它描述目标体验与核心场景，不代表所有能力已经实现或通过发布验收，也不替代具体功能的实现计划。

与[既有产品说明书](overseas-recruiter-agent-v1/product-spec.md)配合阅读：本文更新产品定位、核心场景与交互组织原则；旧说明书中与本文冲突的首页或模块组织方案，以本文为准。具体数据与业务规则仍需结合对应规格和当前实现核对。

## 产品定位

Hirelix 是替猎头持续推进工作的个人 AI Agent。目标用户是海外英语国家的独立猎头与精品猎头公司顾问，首版聚焦桌面浏览器体验。

用户交给 Agent 的是一个工作目标，以及完成它所需的资料。Agent 理解上下文，执行已授权的工作，交付结果，并能在后续对话中接着推进。

英文产品类别保持 **Personal AI Agent for Headhunting**。长期助理的价值体现在持续理解客户、候选人、职位、工作偏好和明确约定，并在下一次工作中正确使用这些信息。

## 八个核心场景

| 场景 | 用户交代的目标 | Agent 应承担的工作 | 用户获得的结果 |
| --- | --- | --- | --- |
| 接下招聘需求 | “客户要招一个产品负责人，这是 JD 和电话记录。” | 整理真实需求、关键条件、待澄清问题和评估标准；保存客户偏好，并随反馈更新 | 可用于后续匹配和沟通的职位理解，以及真正需要补充的信息 |
| 积累和理解候选人 | “这是今天聊的人，简历和聊天记录都在这里。” | 识别已有候选人，整理经历、能力、意愿与沟通信息；按授权更新档案，保留来源和时间 | 能持续使用的候选人资料，避免重复录入和遗忘历史沟通 |
| 从已有资源中找合适的人 | “我认识的人里，谁适合这个职位？” | 检索用户自己的候选人库，结合具体职位判断匹配度，解释推荐理由、风险和缺失证据 | 有依据的人选建议，包括容易被遗忘的已有候选人 |
| 准备候选人沟通 | “我下午要和 Mira 聊，帮我准备一下。” | 回顾历史沟通，整理本次目标、核实问题和职位介绍；会后接收笔记，按授权更新判断和下一步 | 有上下文的沟通准备，以及会后可以继续推进的工作 |
| 向客户推荐候选人 | “把这三个人推荐给客户，讲清楚各自的优势。” | 根据真实证据形成推荐材料，按客户习惯调整表达，检查对外分享范围，在对话中完成修改与交付 | 可查看、修改、导出或在明确授权后发送的推荐材料 |
| 推进面试和反馈 | “客户觉得她行业经验不够，但愿意再聊一次。” | 将反馈关联到人选和职位，更新评估标准，准备后续沟通与面试材料，明确下一步由谁在什么时候做 | 连贯的推进记录和清楚的下一步，反馈能影响后续工作 |
| 跟进关系和约定 | “他年底才考虑机会，11 月再联系；客户周五要一次进展。” | 记住明确约定，在合适时间提醒或执行已授权的准备工作，带上相关上下文 | 可兑现的跟进和交付，用户无需重新解释前因后果 |
| 回顾工作并安排下一步 | “今天我最该推进什么？” | 汇总正在推进的职位、人选与承诺，识别停滞、到期和等待反馈的事项，给出有依据的行动建议 | 重要事项与具体行动建议，并能继续委托 Agent 执行 |

候选人与职位需要双向连接：既支持“这个职位适合谁”，也支持“这个人适合哪些已有机会”。匹配判断始终属于具体的候选人与职位组合，不建立脱离职位的全局“好候选人”标签。

已有资源匹配以用户自己的资料为基础；本文不恢复已经退出产品的独立外部付费人才寻访链路。

## 贯穿所有场景的能力

### 持续记忆与上下文

记住用户明确表达的工作方式、客户偏好、沟通历史和约定，让“按上次的方式写”“接着推进这个人”能够成立。

区分事实、判断和用户偏好，保留信息来源与时间。发现事实冲突或信息可能过期时明确指出；用户应能纠正或要求忘记信息。不能把长期助理解释为无限记忆或自动知道外界变化。

### 连续执行与交付

接收资料、查找信息、分析、撰写、修改、保存和交付应形成连续过程。明确授权且没有歧义的工作直接完成；只有身份、事实冲突或影响任务的缺失信息才需要用户决定。分析和讨论本身不授权修改资料。

工作进度、结果与失败恢复留在对应对话中；从候选人、职位或文稿页面发起的操作，在原页面也能看到状态并恢复。完成时说明实际结果；失败时说明具体阻塞，不能把“准备执行”当成交付完成。

### 行动授权与信息边界

资料整理和材料准备在已授权范围内直接执行。对外发送、披露私人信息或作出承诺需要明确授权；准备推荐材料本身不等于允许发送或分享全部私人资料。

需要用户决定时，提出具体问题并说明它影响什么。普通草稿不自动构成审批任务，Agent 也不能自行代表用户联系候选人或客户。

## 首版需要打通的完整工作链

**接需求 → 找到已有候选人 → 准备沟通 → 形成推荐 → 吸收反馈 → 持续跟进。**

优先保证这条工作链的连续性：前一步产生的信息应能被后一步使用，用户能跨对话继续工作，客户反馈能改变后续判断，明确约定能被可靠执行。

八个场景是能力地图，不要求每个场景对应一个独立模块、入口或页面。具体实现应复用现有资料、对话和执行能力，避免为场景名称增加重复实体。

## 交互与信息架构原则

产品围绕正在推进的工作及其对话组织。候选人库、职位库、文稿和日程支撑工作，并保留按需查阅和管理的入口。

首页应优先支持：

1. **交代新工作。** 输入目标与资料是主要入口。
2. **继续已有工作。** 用轻量入口回到有上下文的对话，说明目前进展。
3. **处理真正需要决定的事项。** 说清具体问题、原因及影响，回到对应工作处理。

Agent 完成推荐稿后，应在原对话中交付，用户可以继续说“缩短一点”“补充匹配理由”。用户不应为了继续工作，被迫进入独立的文稿管理流程。

只有存在真实待决事项时才突出确认请求。例如，需要确定材料的使用范围时，可以问：“这份材料只用于内部讨论，还是准备发给客户？”如果用户已经明确授权，则不重复询问。

### 当前“待审核的草稿”问题

讨论时的首页实现从已保存文稿中读取最近两条 `status = draft` 的记录，并统一展示为“待审核的草稿”。这一筛选不能证明用户尚未看过，也不能证明当前存在必须审批的事项。

后续设计不能仅凭草稿状态生成用户待办。首页需要围绕工作进展和真实待决问题组织；文稿作为工作成果保留，必要时以明确类型与用途展示。仅把标题改成“最近的文稿”不足以完成整体体验调整。

## 设计与验收时应回答的问题

- 用户能否用工作目标发起任务，而无需先理解产品内部模块？
- Agent 能否使用已有资料和历史反馈，避免让用户重复解释？
- 用户是否知道已经完成什么、还缺什么，以及下一步是什么？
- 所有确认请求是否对应真实缺失信息或授权边界，而非机械审批？
- 成果是否已实际保存并可查看、修改和继续使用？
- 跨对话继续工作、约定跟进和失败恢复是否有真实链路证据？

具体功能的上线状态和验证结果应记录在相应验收文档中，不能由本文的目标描述推断。
