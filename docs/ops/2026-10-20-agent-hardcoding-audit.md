# Agent 案例硬编码审查与收敛

日期：2026-10-20。范围：前两轮提交 `f7219ee6`、`c2b6ae47`，以及它们所在的当前 JD 接收、职位修订、私人库检索、评估和成果生成链路。仅本地修改与验证，不推送、不部署。

## 审查结论

在这条活动链路中，没有发现按测试客户、候选人姓名、具体职位、行业关键词或测试 ID 分流判断的代码，也没有将“接收 JD → 保存 → 匹配”编成必须执行的工作流。工具由 ReAct 根据委托、上下文与实际回执选择；检索相似度不直接决定候选人是否适合。该结论不代表逐行审计整个仓库或保证任意模型措辞都正确。

确实存在由历次验收积累的提示词重复和过细例子。这些不是案例判断分支，但继续堆叠会增加维护负担，并让通用约束被例子淹没。本次做了如下收敛：

| 位置 | 问题 | 处理 |
| --- | --- | --- |
| `agent-model.ts` / runtime 首轮参数 | 新对话第一步无条件关闭思考，覆盖了已配置的推理策略，与实际任务复杂度无关 | 移除首轮覆盖，首轮与后续步骤均遵循模型配置；没有增加意图分类或问候专用分支 |
| runtime 系统提示词 | 存在重复强调和平台访问说明 | 试验过合并，但出现事实边界回归；最终保留原有系统提示，只删除无条件首轮推理覆盖。重复指导不按案例执行分支，不能为减字损失必要约束 |
| `roles.ts` | 证据规则反复列举办公天数、薪资、斜杠、管理人数等案例细节 | 收敛为最新要求优先、逻辑关系与阈值、来源精度、复合条件逐项核验、事实维度独立等规则 |
| `assessment.ts` | 评估标签的含义夹在通用职位证据规则中 | 将标签含义写回共享 assessment schema，由聊天保存评估和单独评估共同复用；仍由模型判断，没有新增确定性打分或排除规则 |
| `deliverables.ts` | 特定城市例子、逐句禁用示例及“无活动时只说固定一句话”限制 | 改为通用的来源覆盖边界，允许按用户要求同时说明已确认职位背景，并区分背景和本期活动 |

必要的事实区分仍保留：管理团队人数不自动证明直属关系或招聘绩效权限；“未知”不等于零，也不能先给一个确定数字再补一句未知。它约束所有相关专业证据，不按某个案例判定候选人通过或淘汰。

## 代码与模块边界

核对了 runtime 的工具选择和修复入口、工具 schema 与执行、内部写入授权、`conversation-actions.ts` / `roles.ts` 的事务更新、候选人/职位检索、评估保存及三个内置 Skill。没有增加实体、依赖、额外 Agent、场景路由或自动串联动作。

保留的确定性约束负责用户隔离、来源归属、授权引用、版本冲突、幂等、数据结构及资源上限。工具名列表、状态枚举、分页、批量大小和 JSON 结构修复属于能力协议或资源约束；不根据职业、技能词或人名替代模型判断。结构修复仍不能添加事实、授权或来源。

## 复测设计与中间发现

- 保留 JD 原文、身份隔离、不改候选人事实、每条反馈来源、当前职位版本评估等原有业务断言。
- 新增质量管理岗位的对照：同一个人的相同证据，在“两项同时满足”与“任一条件即可”的当前要求下得到不同结论；旧 JD 不覆盖已明确修订的 brief。
- 旧接收测试遗漏了“建立职位记录”等同义表达，扩展其措辞识别；未放松不得擅自写入、不得自动研究等断言。
- 旧进展报告测试在未要求预算时却强制断言预算必定出现，改为用户明确要求包含预算与办公条件，再检查当前 brief 优先及活动证据边界。
- 原先“每个工具调用必须一次成功”的断言与 ReAct 的纠错机制不符；改为检查最终任务完成和持久结果，并保留完整错误及恢复轨迹。某轮出现来源校验拒绝后，Agent 读取记录并纠正，安全边界没有绕过。另给来源字段补上记录 ID 与消息/实体 ID 的区别。
- 意向断言原来跨整句匹配“unknown”，会把未知分享权限错误归给已确认意向；直属人数断言也会将“not as five direct reports”视作肯定陈述。修正谓词范围，保留明确要求直属关系未知以及禁止肯定人数的检查。
- 当前 brief 明确写“旧限制已取消”仍包含旧条件文字，不能据此认定旧条件继续生效。用满足替代条件、却不满足旧条件的人选是否被重新考虑来验收，保留新阈值、预算、角色版本与判断断言。
- 精简初稿曾使模型把“管理五人”回答成“五位直属”，甚至先报数字再加免责声明。没有把这些轮次计为通过，也没有放松该断言；保留了明确的通用报告关系定义与未知值回答规则。

首轮快速路径下还观察到回复语言和可选联系人前提的失守。移除快速路径的理由是推理配置应按真实请求一致生效；本次有限对照不构成所有错误根因或性能分布的证明。
